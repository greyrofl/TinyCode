# Реальная проверка локальных моделей

Дата: 2026-11-03. Ollama 0.32.3; NVIDIA RTX 3050, 8 ГБ VRAM.

Это историческая диагностика поведения **0.3**, до исправлений
[`0.4`](RELEASE_0.4.md). Текущий benchmark runner использует текущий код;
точные исходные requests/responses сохранены в артефактах указанных прогонов.

Это диагностический прогон, а не статистический рейтинг моделей. Один seed и
одна маленькая задача не позволяют утверждать, что какая-либо модель в целом
лучше. Qwen3.5-2B-abliterated и Qwen3-8B различаются не только размером, но и
поколением, дообучением, квантованием и chat template.

## Методика

- Настоящий `ChatService` и Ollama provider, не mock.
- Каждый прогон получает новую временную папку и новую сессию.
- Задача: исправить off-by-one в `takePage`, не изменяя тесты.
- Исходно 2 из 4 тестов не проходят. Успех проверяется независимым `node --test`.
- 26 tools; `num_ctx=8192`, `num_predict=2048`, seed 42, максимум 16 шагов.
- Промт задачи общий: «исправь падающие тесты», без подсказки правильной формулы.
- Тестовый пример корзины из `promt.md` не используется: он содержит готовое
  исправление и загрязняет оценку на том же примере.
- Загрузка модели измеряется отдельно от agent-loop.
- Фиксируются raw NDJSON, model requests, reasoning/text отдельно, tool errors,
  `done_reason`, token counts, скорость и CPU/GPU placement.
- Shell approval разрешает только `npm test` и ограниченные варианты `node --test`.
- Пользовательский конфиг и рабочие файлы не изменяются. В этом наборе тестов
  14B не использовалась.

Повторение:

```bash
npm run build
node scripts/evaluate-models.mjs 2b-current 120
node scripts/evaluate-models.mjs 8b-q6-current 180
node scripts/evaluate-models.mjs 8b-q6-no-thinking 150
node scripts/evaluate-models.mjs 8b-q6-recommended 150
```

Один model run выполняется за раз. Все артефакты остаются в
`%LOCALAPPDATA%/Temp/opencode/tinycode-model-evaluation/`.

## Результаты

| Режим | Parallel | Время без загрузки | Шаги | Результат |
| --- | ---: | ---: | ---: | --- |
| Qwen3.5-2B Q4, текущий промт | фактически 1 | 15,4 с | 16 | Не исправила, 9 блокировок повторов |
| 2B, явно заданная последовательность в user prompt | фактически 1 | 23,7 с | 16 | Не исправила |
| 2B, компактный промт с валидным примером JSON | 1 | 20,8 с | 16 | Не исправила; JSON корректный |
| Qwen3-8B Q6, текущий промт, default thinking | 4 | 180 с (deadline) | 2 | Не закончила до ограничения времени |
| Q6, только `think: false` | 4 | 150 с (deadline) | 2 | Reasoning перешёл в обычный content |
| Q6, `/no_think`, текущий sampling | 4 | 150 с (deadline) | 16 | Неверные изменения, тесты не проходят |
| Q6, `/no_think`, рекомендуемый sampling | 4 | 150 с (deadline) | 14 | Неверные изменения, тесты не проходят |
| Q4, `/no_think`, рекомендуемый sampling, текущий промт | 4 | 116,2 с | 16 | Не исправила |
| Та же Q4 и текущий промт, один parallel slot | 1 | 26,7 с | 11 | Объяснила правильную формулу, но не применила её |
| Q4, компактный конкретный промт | 1 | **15,6 с** | **7** | **4/4 теста прошли**, тесты не изменены |
| Q6, компактный промт с валидным примером JSON | 1 | **94,4 с** | **8** | **4/4 прошли**, тесты не изменены |

Было 12 прогонов: ещё один черновой компактный промт на 2B использовал
невалидный JSON-плейсхолдер `{...}`. Модель копировала его и получила 3 ошибки
парсинга. Этот вариант отдельно исправлен и повторён (`2b-short-valid`); он не
используется как доказательство ограничения модели по синтаксису.

В обоих успешных прогонах независимый `node --test` подтвердил результат, все
защищённые файлы (tests, manifest, README, AGENTS) остались неизменны.

У 2B malformed JSON не было. Она застряла на поиске файлов, не перейдя к запуску
тестов или изменению кода. Например, `find_files("*.test.js")` не находит файлы
во вложенном `test/`, а `search_text("test.*")` по умолчанию ищет буквальный текст,
не regex. Скудное описание аргументов в системном промте усугубляет ошибку.

У 8B первый request: 1014 generated tokens, 4720 символов thinking, около
6,5 tokens/s, 159,3 с до первого tool call. JSON корректный. Общая остановка на
180-й секунде — ограничение benchmark, а не доказательство неспособности
закончить задачу. `num_predict=2048` в завершённом request не был исчерпан.

## Память GPU: обнаружена конкретная причина

На основной системе `OLLAMA_NUM_PARALLEL=4` установлен одновременно в User и
Machine environment. Значение не менялось. По логам основной Ollama:

| Модель/режим | GPU layers | Общий KV-кэш |
| --- | ---: | ---: |
| Q6, parallel=4 | 20/37 | 4608 MiB |
| Q4, parallel=4 | 24/37 | 4608 MiB |
| Q6, отдельный server parallel=1 | 31/37 | 1152 MiB |
| Q4, отдельный server parallel=1 | 37/37 | 1152 MiB |

Временный сервер запускался только на `127.0.0.1:11436`, с process-local
`OLLAMA_NUM_PARALLEL=1`, без изменения основного Ollama, cache type, quantization
или настроек Windows. Он остановлен после проверки.

На Q4 скорость выросла примерно с 8 до 28 tokens/s после перехода с CPU/GPU на
полный GPU. Q6 даже с одним slot не помещается целиком при текущей свободной VRAM
и 8k context: скорость в успешном прогоне около 10 tokens/s. Сравнение размеров
GGUF на диске не учитывает KV-кэш, compute buffers и память других приложений.

## A/B промта

На Q4, одном slot и одинаковом sampling длинный текущий промт не обеспечил
выполнение задачи. Компактный вариант оставил те же 26 инструментов, но убрал
повторяющиеся общие правила и явно пояснил семантику `edit_file`:

> `oldText` — весь текст, который удаляется; замена заголовка функции не заменяет
> её тело. Не отправлять одинаковые `oldText` и `newText`.

Полный первый input уменьшился с 2628 до 1312 токенов по счётчику Ollama. Это
счётчик всего входа (system, user, template), не только system prompt.

Менялись одновременно формулировки и длина: успех не доказывает, что одно лишь
укорачивание любого промта улучшит результат. 2B не выполнила задачу и с компактным
валидным вариантом, поэтому ей требуется отдельная адаптация и дальнейшие тесты.

Контрольный Q6-прогон также исправил ошибку, но первый edit оказался неверным;
модель прочитала тест и восстановилась вторым edit. Финальный ответ всё ещё
содержал reasoning в обычном content: soft `/no_think` не является абсолютным
hard switch для этого импортированного template.

## Подтверждённые проблемы интеграции

1. `showReasoning` управляет отображением, но provider не отправляет `think` в
   `/api/chat`. Скрытая панель не выключает вычисление reasoning.
2. Q6 при 8192 context не размещается полностью в VRAM. `/api/ps` сообщает
   `size_vram=6236196044`, `size=11747165468`; это метрики памяти Ollama, не процент
   GPU-слоёв. Во время inference GPU использует около 7576 из 8192 MiB.
3. TinyCode переопределяет Qwen3 sampling: `temperature=0.2`, `top_p=0.9`,
   `repeat_penalty=1.05`; модельный manifest рекомендует другие значения.
   Сам по себе этот факт не доказывает, что низкая temperature вызвала цикл.
4. У инструментов в промте сохраняются типы аргументов, но теряются их подробные
   описания и defaults. Семантика glob/regex/line range недостаточно явная.
5. Anti-loop guard блокирует действие, но не гарантирует выхода модели из
   планировочного цикла: 2B продолжала повторять запросы до 16-го шага.
6. Установленные HF-модели не возвращают объект `thinking` metadata в
   `/api/show`. Поэтому поддержку `think: false` необходимо проверять по реальному
   ответу, а не предполагать по названию модели или переключателю UI.
7. `think: false` у конкретного HF Go-template не прекратил вычисление reasoning:
   оно оказалось в `content`, включая `</think>`. `/no_think` сократил время до
   первого tool call с 159,3 до 7,6 с, но не устранил все такие утечки.
8. `edit_file` сообщает успех даже при `oldText === newText`. Это ошибочно
   считается изменением projectVersion и позволяет обходить repeat guard.
9. Модель несколько раз подставляла целую функцию вместо одного заголовка,
   оставляя старое тело на месте. Нужны ясные аргументные описания и полезный
   post-edit diff/текущее содержимое, а не только «Edited».
10. `ChatService` принимает ответ-план без tool calls как завершение. В одном
    прогоне модель сказала «сейчас исправлю», но файл не изменился. Надёжный
    критерий успеха должен опираться на фактические действия и проверку.

Список read-only tools тоже не гарантирует качество планирования. В текущем
2B-прогоне исходное расположение `test/` было известно после первого `list_dir`,
но модель продолжила искать тесты внутри `src/` и не запустила команду из
`package.json`. Это ошибка исполнения агентского плана, а не ошибка JavaScript.

## Вердикт и приоритеты

Ошибки нельзя списать исключительно на число параметров. Есть подтверждённые
проблемы промта, adapter protocol, loop control и ресурсов inference. После
исправления условий 8B выполнила ту же задачу, тогда как проверенная 2B продолжала
застревать. Это не рейтинг всех 2B/8B-моделей.

Приоритеты следующих изменений:

1. Один parallel slot для единственного локального coding-agent; Q4 или иной
   реально помещающийся режим, если важна скорость на 8 GB.
2. Явные model profiles: sampling, generation thinking control, compatibility
   с GGUF template. `showReasoning` оставить только display-настройкой.
3. Компактный stage-aware prompt, валидные небольшие JSON-примеры и сохранённая
   семантика критичных аргументов.
4. No-op detection, ограничение серии одинаковых ошибок, post-edit feedback и
   честный критерий завершения задачи.
5. Для 2B — отдельный формат/набор активных tools, короткие этапы, несколько seeds
   и новые задачи до выводов о самостоятельном agent mode.

В рамках этого benchmark изменены только диагностический скрипт и отчёт, а не
default-промт, provider, пользовательская конфигурация или системное окружение.

## Официальные рекомендации

- Qwen3 thinking: temperature 0.6, top_p 0.95, top_k 20, min_p 0.
- Qwen3 non-thinking: temperature 0.7, top_p 0.8, top_k 20, min_p 0.
- Greedy decoding не рекомендуется; temperature 0.2 не равно greedy.
- В Ollama thinking задаётся верхнеуровневым `think`, не `options.think`.
